How to Use This Guide
This is the master implementation document for VaultDB. It consolidates the project specification, scope decisions, architecture, staged implementation plan, C-learning objectives, testing requirements, Git/GitHub requirements, documentation requirements, and final submission checklist.
Build the project incrementally. Each phase should compile, run, and be tested before the next phase is started. Do not attempt to implement the entire database engine in one code dump.
The core project must be implemented in C. External database systems such as MySQL, PostgreSQL, and SQLite are not to be used as the database engine.
1. Project Definition
VaultDB is a lightweight, offline-first embedded database engine built from scratch in C. It explores persistent storage, dynamic memory management, query processing, record management, searching, and indexing.
VaultDB is deliberately smaller than a production database. The purpose is to demonstrate database and systems concepts clearly rather than recreate SQLite.

Core principle
VaultDB is a database engine, not a generic CRUD application. The example business domain is only a way to demonstrate the engine.
2. Problem Statement and Real-World Story
Problem Statement
Small businesses, local shops, clinics, pharmacies, workshops, and similar environments may need simple persistent local data storage without depending on a large database server or constant internet connectivity. VaultDB explores whether a lightweight local database engine can provide basic persistent storage and query functionality with a small resource footprint.
Example Story
A small shop can use a local file such as shop.db to store product data. The shop is not the product; VaultDB is the reusable database engine.

7. Data Model
Record
struct Record {
    int id;
    char *name;
    int price;
    int stock;
};
The current record model uses a dynamically allocated name. record_create allocates the structure and name; record_destroy releases name first and then the structure.
Table
struct Table {
    char *name;
    struct Record *records;
    int record_count;
    int capacity;
};
record_count is the number of records currently used. capacity is the number of record slots currently allocated.
capacity = 4
record_count = 2
[Record][Record][empty][empty]
if record_count == capacity:
    grow the allocation
Database
A later database-level structure will manage tables and database metadata. It should be introduced after the record/table layer is stable.

9. Query Language
VaultDB supports a deliberately small SQL-like language, not full SQL.
CREATE TABLE customers (id, name, phone);
INSERT INTO customers VALUES (1, "Alice", "9876543210");
SELECT * FROM customers;
SELECT * FROM customers WHERE id = 1;
UPDATE customers SET phone = "9999999999" WHERE id = 1;
DELETE FROM customers WHERE id = 1;
Suggested grammar
CREATE TABLE <name> (...);
INSERT INTO <table> VALUES (...);
SELECT * FROM <table>;
SELECT * FROM <table> WHERE <column> = <value>;
UPDATE <table> SET <column> = <value> WHERE <column> = <value>;
DELETE FROM <table> WHERE <column> = <value>;

11. Searching and Indexing
Linear search
for each record:
    compare requested key
    if match:
        return record
Worst-case time complexity: O(n).
Simple indexed search
Sorted index
    ↓
Binary search
    ↓
candidate record location
    ↓
record lookup
Binary search over a sorted index is O(log n) for the search itself, but maintaining the index adds insertion/deletion work.
A B-Tree/B+Tree is optional and should only be considered after the simpler system is stable.
12. Memory Management
Every allocation needs a clear owner.
Check malloc/calloc/realloc results.
Free all owned memory.
On partial failure, clean up prior allocations.
Avoid double-free and use-after-free.
Do not lose the only pointer to allocated memory.
Record lifecycle
record_create()
 ↓ malloc Record
 ↓ malloc name
 ↓ copy name
 ↓ use
 ↓ record_destroy()
 ↓ free name
 ↓ free Record
Table lifecycle
table_create()
 ↓ malloc Table
 ↓ malloc table name
 ↓ malloc record array
 ↓ use
 ↓ table_destroy()
 ↓ free owned allocations
When inserted records own dynamically allocated names, table destruction must free those names before freeing the record array.

24. Scope Control Rules
Build the simplest working version first.
Do not add features merely because they sound impressive.
Do not implement full SQL.
Do not jump to B-Tree before the basic engine works.
Do not optimize before establishing correctness and a baseline.
Keep parser, executor, and storage responsibilities separate.
Do not sacrifice the MVP for bonus features.
Working + understandable + well-tested is more valuable than huge + incomplete.
